# Лекция 2. Архитектура ИИ-сервиса: Антифрод

## Архитектурная схема
1. **Клиент (Мобильное приложение / Терминал)** → передает данные о транзакции.
2. **API Gateway** → маршрутизирует запрос и проверяет токены.
3. **Сервис Антифрода (CatBoost)** → быстро считает скор (вероятность фрода).
4. **Сервис Объяснений (LLM / YandexGPT)** → вызывается только если скор высокий, генерирует текстовое пояснение.
5. **База данных алертов** → сохраняет результат для операциониста.

## Обоснование режима обработки
**Выбор: Stream (Потоковая обработка).**
*Почему:* Транзакцию нужно проверить *в момент* оплаты. Если мы будем ждать ночного пересчета (Batch), мошенник уже выведет деньги или клиент не сможет оплатить покупку. Ответ нужен за миллисекунды.

## Обоснование технологического стека
*   **Основная модель: CatBoost (Classical ML).** 
    *   *Паттерн:* Model-as-a-Service (отдельный микросервис).
    *   *Почему:* Нам нужна высокая скорость (инференс < 50мс) и работа с табличными данными. CatBoost отлично работает с категориальными признаками "из коробки".
*   **LLM-слой: YandexGPT.**
    *   *Почему не LLM для самой детекции?* LLM слишком медленная и дорогая, чтобы проверять каждую покупку кофе. CatBoost делает "грязную" работу быстро, а LLM добавляет "интеллект" (объяснение) только там, где это нужно (при высоком скорe).

## Три узких места архитектуры
1.  **API LLM-провайдера:** Если внешний сервис YandexGPT упадет или будет долгий ответ, операционист не увидит объяснение. *Решение:* Возвращать шаблонный текст при ошибке.
2.  **Feature Store / Сервис фичей:** Рассинхрон признаков между обучением и продом (training-serving skew). *Решение:* Использовать единый код предобработки.
3.  **Очередь событий (при скачке нагрузки):** Если поток транзакций вырастет в 10 раз (Black Friday), сервис может не справиться. *Решение:* Масштабирование подов в Kubernetes.
