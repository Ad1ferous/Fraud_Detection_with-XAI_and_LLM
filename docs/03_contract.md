# Лекция 3. Проектирование ML-сервиса контракты и версионирование

## OpenAPI-спецификация (упрощенно)
*   **Endpoint:** `POST /v1/fraud/check`
*   **Request (Вход):**
    ```json
    {
      "transaction_id": "uuid-123",       // string, обязательное
      "amount": 15000.50,                 // float, обязательное
      "timestamp": "2023-10-27T10:00:00Z",// string (ISO 8601), обязательное
      "merchant_category": "electronics"  // string, обязательное
    }
    ```
*   **Response (Выход - Успех 200):**
    ```json
    {
      "is_fraud": true,                   // boolean
      "risk_score": 0.92,                 // float (от 0 до 1)
      "explanation": "Аномально высокая сумма для этого магазина...", // string
      "model_version": "catboost_v2"      // string
    }
    ```
*   **Errors:**
    *   `400 Bad Request`: Неверный формат суммы или отсутствует timestamp.
    *   `503 Service Unavailable`: Сервис LLM недоступен (но решение о фроде и risk_score все равно вернуты).

## Стратегия версионирования
Мы используем семантическое версионирование для API и версионирование по дате для модели.
*   **MINOR-изменение (v1.1 -> v1.2):** Мы добавили новое поле `explanation_id` в ответ. Старые клиенты просто его проигнорируют, их код не сломается.
*   **MAJOR-изменение (v1 -> v2):** Мы переименовали поле `risk_score` в `probability`. Это сломает старых клиентов, которые ищут `risk_score`, поэтому мы поднимаем мажорную версию и поддерживаем `/v1/` и `/v2/` параллельно.

## Сценарий нарушения контракта
*   **Сценарий:** Клиентское приложение (обновленное) начинает передавать `amount` не в рублях, а в копейках (целое число `1500050`), не предупредив команду ML. Модель воспринимает это как транзакцию на 1.5 миллиона рублей и блокирует её.
*   **Как обнаружить раньше пользователей:** Настроить строгую валидацию входных данных на уровне Pydantic (FastAPI) и добавить интеграционные тесты, которые проверяют границы значений (например, `amount` не может быть больше 10_000_000).
