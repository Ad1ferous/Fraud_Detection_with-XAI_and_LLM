# Лекция 4. MLOps как эволюция DevOps

## MLOps-профиль по 9 блокам

| Блок профиля | Как выглядит в нашем кейсе | Что можно улучшить следующим шагом |
|---|---|---|
| 1. Задача и пользователь | Оценить риск банковской транзакции в реальном времени и вернуть решение (approve / review / block) + понятное объяснение. Пользователь системы — платёжный шлюз и операторы антифрод- мониторинга. | Добавить явную бизнес-метрику успеха: снижение потерь от фрода при сохранении доли ложных блокировок ниже X%. |
| 2. Данные | История транзакций клиентов за 90–180 дней (сумма, время, устройство, geo, merchant, поведение). Ручная проверка: отсутствие явных дублей и корректность меток фрода на обучающей выборке. | Внедрить автоматическую data validation (проверка пропусков, диапазонов, свежести данных) перед каждым переобучением. |
| 3. Модель / логика | Основная модель — градиентный бустинг (LightGBM/CatBoost) + SHAP для объяснимости. LLM генерирует текстовое объяснение на основе SHAP-значений. | Добавить простой калибровочный слой или threshold-оптимизацию под стоимость ошибок разных типов. |
| 4. Эксперименты | Варианты моделей и гиперпараметров сравниваются в MLflow. Логируются параметры, метрики, feature importance и примеры SHAP. Воспроизводимость частичная (есть run_id, но данные не всегда версионируются). | Начать логировать hash датасета и версию feature-store вместе с каждым экспериментом. |
| 5. Проверки качества | Перед выкладкой проверяется: модель не возвращает пустой ответ, latency &lt; 300 мс, доля block не превышает исторический порог, объяснения не пустые. | Добавить автоматический тест на устойчивость к крайним случаям (новая география, крупная сумма ночью, смена устройства). |
| 6. Запуск и обновление | Новая версия модели выкладывается через canary (5–10% трафика) после ручного approval. Откат возможен по кнопке. Полностью автоматического retrain пока нет. | Сделать автоматический rollback при росте latency или доли ошибок выше порога. |
| 7. Мониторинг | Смотрим: доля block / review, latency p95, data/feature drift, долю пустых объяснений, количество ручных эскалаций. | Добавить алерт в реальном времени при резком росте drift или падении качества объяснений. |
| 8. Текущий уровень зрелости | Уровень 1 (автоматизация пайплайна частично есть). Есть MLflow, canary-деплой и базовый мониторинг, но data validation и автоматический retrain ещё ручные. | — |
| 9. Следующий шаг | Внедрить автоматическую data validation + логирование версии данных в каждый эксперимент. | Без этого шага через 6–9 месяцев команда не сможет быстро понять, почему модель деградировала, и будет терять время на поиск причины вручную. |

## Краткое обоснование уровня

Мы не на уровне 0 (уже есть MLflow, санагу и мониторинг), но ещё не на уровне 2 (нет полного автоматического цикла переобучения и продвинутого мониторинга с авто-реакцией). Поэтому честно фиксируем уровень 1.
