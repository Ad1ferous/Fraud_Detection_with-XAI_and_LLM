# Лекция 8. Тестирование ИИ-компонентов в системе

# Тестовая стратегия ИИ-компонента (для вебинара 8)

*Кейс: сервис детекции подозрительных транзакций (XAI + LLM-объяснения)*

**Цель:** убедиться, что ML-сервис стабильно возвращает корректное решение (approve / review / block), объяснение и не ломает платёжный поток.

## Уровни тестирования

| Уровень | Что проверяем | Примеры тестов / инструменты |
|---|---|---|
| Unit | Модель и отдельные функции: формат выхода, вероятности, feature importance, устойчивость к выбросам, метрики качества. | pytest: 8+ тестов модели; проверка predict / predict_proba; минимальные пороги F1, ROC-AUC, Precision, Recall. |
| Integration | Связка API ↔ модель ↔ Feature Store / БД. Контракт /v1/score, коды ошибок, latency, версия модели в ответе. | Тесты контракта (schema, 422/404/503); проверка, что explanation и model_version возвращаются; таймаут \< 300 мс. |
| E2E | Полный путь: платёжный шлюз → антифрод → решение → (опционально) LLM-объяснение. Бизнес-сценарии. | Сценарии: обычный платёж; крупная ночная сумма; новое устройство; недоступность ML-сервиса → fallback в review. |

## Приоритеты и покрытие

- Критично: контракт API, отсутствие падений на выбросах, наличие explanation, latency.
- Важно: Recall не проседает ниже порога, decision согласован с risk_score.
- Желательно: калибровка вероятностей, устойчивость к drift, fairness по стране/каналу.

## Учтённые слабые места

В unit-тестах зафиксирован невысокий Recall (~0.73) и чувствительность к threshold=0.5. В integration/E2E закладываем проверку fallback-поведения и мониторинг доли review/block, чтобы вовремя заметить деградацию.

## Когда запускаем

Unit — на каждый Pull Request/коммит. Integration — на сборку и перед canary. E2E — перед релизом и по расписанию (ночные прогоны ключевых сценариев).
