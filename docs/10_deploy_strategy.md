# Лекция 10. Стратегии деплоя и релиз-процессы.
# Стратегия деплоя антифрод-сервиса банка

Проект: ML-сервис детекции подозрительных транзакций (FastAPI, эндпоинт /V1/score). Сервис возвращает risk_score, decision (approx / review / block) и explanation.

## 1. Выбор и обоснование стратегии

Выбранная стратегия: shadow-запуск → саналу с поэтапным увеличением доли трафика (5% → 25% → 50% → 100%).

Почему не blue-green и не «сразу на 100%». Согласно теории вебинара, blue-green уместен, когда критичен мгновенный откат и допустимы два полных окружения. Для антифрода важнее другое: ошибка модели «тихая» — сервис не падает с исключением, а просто отвечает хуже. Ложные блокировки портят клиентский опыт, пропуски мошенничества дают прямые финансовые потери. Качество на реальном потоке трудно предсказать заранее: тестовая выборка может не отражать сезонность, новые схемы атак и drift признаков. Мгновенный полный переключатель в такой ситуации слишком рискован.

Почему shadow + canary. Shadow-запуск даёт нулевой риск для пользователя: новая модель получает копию трафика и пишет ответы только в лог, решение клиенту по-прежнему отдаёт текущая версия. Это позволяет сравнить поведение моделей на реальных данных до любого влияния на бизнес. Затем canary постепенно наращивает долю реального трафика. Проблема, если она есть, затрагивает сначала малую часть запросов; на любом этапе раскатывание можно остановить или откатить. Такое сочетание прямо соответствует рекомендации курса для кейсов с высокой ценой ошибки и непредсказуемым качеством на проде.

## 2. Критерии успешности релиза

Релиз считается успешным на каждом этапе, если новая версия не хуже текущей по набору метрик. Условия формулируются относительно старой версии, а не «хорошего абсолютного уровня»:

- Recall — не ниже текущего уровня на сопоставимой выборке (нельзя пропускать заметно больше фрода).
- False positive rate (доля ложных block и review среди легитимных операций) — не выше текущего более чем на 5%.
- Error rate (доля ответов 5хх и таймаутов) — не выше текущего уровня.
- Latency p95 эндпоинта /v1/score — не хуже текущей версии более чем на 20% (для банка задержка критична). Recall и FPR — метрики качества модели (связь с практикой вебинара 7 и слабыми местами проекта). Error rate и latency — технические метрики сервиса. Вместе они закрывают и «модель отвечает не хуже», и «сервис стабилен».

## 3. Пороги остановки и отката

Каждый порог задан по формуле: метрика + насколько ухудшилась + за какое время → действие. Два уровня реакции: умеренное ухудшение — остановить раскатывание; сильное — откатить.

- False positive rate вырос более чем на 20% за 1 час → остановить раскатывание, разобрать причину.
- Recall упал более чем на 10% за 1 час → немедленный автоматический откат на предыдущую версию.
- Error rate выше 3% в течение 10 минут → автоматический откат.
- Latency p95 выросла более чем на 50% от типичного значения → остановить раскатывание.

## 4. План отката

План готовится до релиза, а не во время инцидента. Условия быстрого отката: версионирование модели и кода, сохранённые артефакты предыдущей версии, наблюдаемость (алерты по метрикам), чёткие критерии запуска отката.

- Кто принимает решение: дежурный MLOps / AI-инженер. Пороги из раздела 3, помеченные как «автоматический откат», срабатывают без ожидания ручного решения.
- Время реакции: до 15 минут с момента алерта до возврата 100% трафика на предыдущую рабочую версию.
- Что с уже обработанными запросами: транзакции, которые новая версия успела обработать за время инцидента, помечаются в логах model_version и передаются службе безопасности для повторной ручной проверки. Решения арргоре, уже отданные платёжному шлюзу, автоматически не пересчитываются — операция могла быть уже завершена. Критичные block/review при необходимости пересматриваются вручную.

## 5. Схема процесса деплоя

### Последовательность этапов:

- Код и модель готовы (пройдены unit / integration / контрактные проверки).
- Shadow-запуск: новая версия получает копию трафика, ответы пишутся только в лог, на пользователя не влияют.
- Точка решения 1: метрики shadow не хуже текущей версии? Да → сапату 5%. Нет → остановить / откатить.
- Canary 5% → точка решения 2 → canary 25% → точка решения 3 → canary 50% → точка решения 4 → 100% трафика.
- На каждой точке «?» три исхода: продолжить, остановить раскатывание, откатить на предыдущую версию — по порогам из раздела 3.

Итог. Стратегия выбрана по свойствам кейса (высокая цена ошибки, «тихая» деградация модели, непредсказуемость прода), а не «по умолчанию». Критерии и пороги — конкретные числа с действиями. План отката отвечает на три вопроса курса: кто решает, как быстро, что с уже обработанными запросами. Схема содержит более четырёх этапов и точки принятия решений.
