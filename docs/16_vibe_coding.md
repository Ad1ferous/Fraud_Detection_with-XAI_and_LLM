# Лекция 16. Vibe-coding, этика, безопасность 

## 1. Риски дрейфа данных (Drift)
В нашем проекте (антифрод) дрейф — это критический фактор, так как мошенники постоянно адаптируются.
* **Data Drift (Дрейф данных):** Резкое изменение распределения признаков. Например, массовый переход пользователей на новый тип устройств или аномальный рост транзакций в праздничные дни.
* **Concept Drift (Концептуальный дрейф):** Изменение тактик мошенников. Старые паттерны (например, множество мелких транзакций) перестают работать, мошенники переходят на крупные единичные списания.
* **Target Drift (Дрейф целевой переменной):** Изменение базовой доли мошеннических транзакций (например, резкий всплеск фрода перед майскими праздниками), из-за чего модель может начать «паниковать» и выдавать больше ложных блокировок.

**Стратегия реагирования:** Мы используем библиотеку `Evidently` для расчета PSI (Population Stability Index) и контроля доли фрода. Если PSI для ключевых признаков (сумма, время, категория) превышает 0.2, или доля фрода отклоняется от тренировочной более чем на 5%, это сигнал к переобучению. Модель CatBoost переобучается ежемесячно на свежих данных.

## 2. План мониторинга и Алерты
Мы разделяем метрики на технические, бизнес-метрики и метрики LLM-слоя.

* **Технические метрики:**
  * Время ответа FastAPI (p95 latency) — не более 200 мс (без учета LLM).
  * Процент ошибок 5xx на сервисе.
* **Метрики качества модели (ML):**
  * **Recall (Полнота):** Доля пойманных мошенников. Критически важно не пропустить фрод.
  * **Precision (Точность):** Доля реальных мошенников среди заблокированных.
  * **False Positive Rate:** Доля ошибочно заблокированных честных клиентов (не должна превышать 3%).
* **Метрики LLM-слоя (Grok API):**
  * **Latency LLM:** Время генерации объяснения (не более 1.5 сек, иначе операционист будет ждать).
  * **Доля отказов API:** Ошибки 429 (Rate Limit) или 5xx от Grok.
  * **Валидность JSON:** Доля ответов LLM, прошедших проверку на соответствие схеме.
  * **Стоимость (Cost):** Расход токенов на одну транзакцию (чтобы не разорить банк на API).

**Условия алертов (Alerting):**
1. **MLOps-алерт:** Если доля False Positive превышает 3% за последние сутки — сигнал на пересмотр порогов (threshold) модели или ручную проверку.
2. **API-алерт:** Если доля отказов LLM (Grok API) превышает 5% за 15 минут, ИЛИ p95 latency LLM превышает 3 секунды — переключение на fallback-режим (выдача кода фрода операционисту без текстового объяснения).
3. **Data Drift алерт:** Если PSI для признака "сумма транзакции" превышает 0.2 — уведомление Data Scientist о необходимости переобучения.

## 3. Ограничения, риски и этика
* **Этический риск №1: Ложные блокировки (False Positives).** Блокировка карты честного клиента вызывает сильное раздражение. *Решение:* Внедрение Human-in-the-loop (спорные транзакции уходят на ручную проверку оператору, а не блокируются автоматически).
* **Этический риск №2: Предвзятость модели (Bias).** Модель может ошибочно считать фродом транзакции определенных групп клиентов (например, по географическому признаку или возрасту), если в исторических данных их было больше среди мошенников. *Решение:* Регулярный аудит fairness-метрик (доля False Positive по разным демографическим группам) и исключение дискриминационных признаков из обучения.
* **Этический риск №3: Галлюцинации LLM (XAI-слой).** Grok API может сгенерировать текстовое объяснение, не соответствующее реальным причинам блокировки (например, придумать несуществующий признак). *Решение:* Жесткий шаблон промпта с передачей только конкретных SHAP-значений. Валидация ответа LLM по ключевым словам и JSON-схеме.
* **Риск ИИ-агента (из Лекции 14):** Агент-ассистент расследования может зациклиться на вызове `get_client_history`, игнорируя поиск похожих случаев, или использовать устаревшие данные. *Решение:* Внедрение лимита итераций (`max_iterations=5`) и проверка актуальности данных (`timestamp` ответа БД). 
* **Ограничение по данным:** В учебном проекте используются синтетические данные (3000 объектов из `make_classification`). На реальных данных распределение фрода будет сложнее (мошенники используют社交 engineering), и текущая модель (Recall 0.57) потребует калибровки порогов и добавления текстовых фичей (NLP).

## 4. Следующий шаг развития
1. Организовать автоматическое A/B-тестирование новых версий модели через MLflow на 10% трафика для проверки отсутствия деградации Precision на живых данных перед полным раскатом.
2. Внедрить кэширование ответов LLM для типовых случаев фрода (например, «подозрительная транзакция в 3 часа ночи»), чтобы снизить задержку и стоимость вызовов Grok API.
